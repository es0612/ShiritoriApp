## 1. 意図

子供がスマホに話しかけて、アプリとしりとりを続けられるようにする。

- **誰に**: 4〜8歳の子供と、その横にいる親。
- **どんな価値か**: 親の手がふさがっていても、子供が声だけで言葉遊びを続けられる。
- **なぜ作り直すか**: 2025年版（Swift 約2.2万行）は、最大5人・プレイヤー登録・履歴・ルール編集・チュートリアルまで広げた結果、タイマーと状態遷移のバグが収まらず、審査準備の段階で止まった（issue #6）。ユニットテストは現在コンパイルできず、1件も実行されない。核の体験が動く前に周辺を作ったことが原因と見ている。

## 2. 目標・非目標・アンチゴール

### 目標（v1）
1. 【決定】子供 vs アプリの1対1。子供が話す → アプリが判定する → アプリが声で言葉を返す、を繰り返す。
2. 【決定】勝ち負けなし。「ん」で終わる言葉を言っても負けにせず、言い直してもらう。何回つながったかを数える。
3. 【提案】起動から最初の1語まで、ボタン1回で届く。
4. 【提案】App Store 公開まで持っていく（「完成」の定義。オーナーは否定していないが明言もしていない）。

### 非目標（v1 では作らない）
- 複数人プレイ（【決定】v1.1 で足す。別の設計書を書く）
- プレイヤー登録、プレイ履歴、ルール編集、チュートリアル、制限時間、難易度選択
- 【提案】広告・課金・アカウント・ネットワーク通信
- 【提案】日本語以外の言語

### アンチゴール（動いても失敗とみなす状態）
- 子供が負けて泣く、間違いで損をする仕組みが入っている。
- アプリが知らない言葉を「間違い」として弾く。
- 聞き間違いが起きたとき、子供にも親にも直す手段がない。
- 子供の声が端末の外に送られる。
- 核の往復が実機で確かめられる前に、周辺機能が増えている。

## 3. 制約

- **技術スタック**: Swift / SwiftUI / Swift Testing / `@Observable`（リポの `CLAUDE.md` に従う）。
- **開発の進め方**: ユニットテスト中心の TDD（Red → Green → Refactor）。
- **実機確認は TestFlight 経由**。Xcode Cloud が Archive と配信を担う。
  - `Default` ワークフロー: main の変更 → Archive → App Store Connect → TestFlight 内部テスト（グループ `shinya`。2026-11-28 にポストアクションを追加）。
  - `Spike` ワークフロー: `spike/` で始まるブランチ → Archive → TestFlight 内部テスト（グループ `shinya`）。
  - Xcode Cloud は「Latest Release」設定で、手元より新しい Xcode でビルドされることがある（2026-11-23 時点: クラウド 27.2 / 手元 26.6）。
- **人にしかできない確認**: 子供の声での聞き取り、子供が一人で続けられるか。シミュレータと合成音声では代用できない。
- **対応 OS**: 【提案】iOS 18.0 以上。iPhone は縦向きのみ。iPad は全方向（iPad の縦固定には全画面指定が要り、App Store の要件に触れるため）。

## 4. アプローチ

### 検討した3案
| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A. 同じリポで組み直す** | 旧コードはタグでしまい、main を核だけの新構成にする。使える部品はテストごと移植 | 履歴・Bundle ID・ASC の設定を引き継げる。核にすぐ着手できる | 旧コードの削除という大きな差分が1回出る |
| B. 今のコードを直しながら減らす | 動く状態を保ちつつ機能を削る | 段階的 | 2.2万行とコンパイルできないテスト群の片付けが先に要り、核に届くまでが遠い |
| C. 別リポでゼロから | 新規リポ | 最も身軽 | 移植できる部品と経緯を手放す。ASC のアプリ登録や Xcode Cloud を作り直す |

**【決定】A 案。**

### 音声認識の方式（試作の結果）
`spike/speech-compare` ブランチの試作（ビルド 43）で、同じ録音を4方式に通して比べた。

- **事実**: 大人の声・お題どおりの12語・ヒント有で、4方式とも12語すべて第1候補で正解。応答は0.1〜0.3秒。漢字で返った結果（牛乳・新幹線・車・猫）は、OS の形態素解析（`CFStringTokenizer`）を使った約20行の変換で正しい読みに戻せた。
- **解釈**: お題どおりの身近な単語では、認識精度はボトルネックではない可能性が高い。方式は精度以外で選ぶ。
- **未確認**: 子供の声、自由に言った言葉、ヒント無し、話し終わりの自動検知。

**【提案】v1 は `SFSpeechRecognizer` を端末内認識（`requiresOnDeviceRecognition = true`）で使う。**
- 理由: 「声を端末の外に送らない」をコード上で明示して保証できる。iOS 18 から使える。試作で満点。
- `SpeechAnalyzer` + `DictationTranscriber`（iOS 26 以上）は、M1 の子供の声での確認で精度が足りなかった場合の差し替え先とする。差し替えられるよう、認識はプロトコルの裏に置く（§6）。
- 【提案】差し替える場合は、対応 OS を iOS 26 以上に上げて1系統にする。18〜25 向けに2系統を持つことはしない（実装とテストが倍になるため）。上げるかどうかは M1 の【人の判断】で決める。確認に使うオーナーの iPhone は iOS 26.6.2。
- `SpeechTranscriber`（長文向け）は使わない。短い単語で断片的な別候補が混ざった。

## 5. 体験の仕様

### 5.1 画面
画面は2つ。**タイトル**と**あそぶ画面**。おわりの表示は、あそぶ画面の上に重ねる。

```
┌────────────────────────┐
│  ⭐ 7かい つながった      [おしまい] │
│                                    │
│        🤖 「りんご」               │
│         り ん【ご】                │
│                                    │
│      つぎは 「ご」 から！          │
│                                    │
│          ┌──────┐                 │
│          │  🎤   │                 │
│          └──────┘                 │
│     きこえた:「ごりら」 [ちがうよ]  │
└────────────────────────┘
```

- 2026-11-28（M1.5）: 回数の行の下に、言葉のつながり（直近 3 つ。例「りんご → ごりら → らっぱ」）の行を足した（`2026-11-28-shiritori-chain-feel-design.md`）。
- タイトル: アプリ名と「はじめる」ボタン1つ。最高記録があれば「さいこう ○かい」を出す。
- 表示する文字はすべてひらがな（子供向け）。

### 5.2 流れ
1. 「はじめる」を押す。
2. アプリが最初の言葉を選び、画面に出して声で言う。
3. 子供がマイクボタンを押して話す。話し終わりはアプリが検知する（§5.5）。
4. アプリが聞き取った言葉を画面に出し、判定する（§5.3）。
5. 正しければ回数を1つ増やし、アプリが続きの言葉を声で返す。3 に戻る。
6. 「おしまい」を押すと、「○かい つながったね！」を出す。最高記録を更新していたら紙吹雪を出す。「もういっかい」「おわる」を選べる。

アプリが話している間は、マイクボタンを押せない。子供がボタンを押してから聞き始めるので、アプリ自身の声をマイクが拾うことはない。

### 5.3 判定（【提案】）
子供の言葉は、読み（ひらがな）にそろえてから、次の順で判定する。

| 順 | 条件 | アプリの反応 | 回数 |
|---|---|---|---|
| 1 | 読みが取れない（無音、英数字など、ひらがなにできない） | 「もういちど いってね」 | 変えない |
| 2 | 最初の文字が合っていない | 「『ご』から だよ」 | 変えない |
| 3 | 「ん」で終わる | 「『ん』が ついちゃった！ もういっかい」 | 変えない |
| 4 | このあそびで既に出た言葉 | 「それ もう いったよ」 | 変えない |
| 5 | 上のどれでもない | ピンポン＋「○かいめ！」 | +1 |

- 2026-11-28（M1.5）: 反応の頭に聞き取った読みを付けて言い返すよう変更した。順 5 は「○かいめ！」の代わりに「すいか！」、順 2〜4 は「すいか？ 『ご』から だよ」のように言う（`2026-11-28-shiritori-chain-feel-design.md`）。

- **辞書にない言葉も受け入れる。** 判定に辞書は使わない。
- 1文字の言葉（め・て・き など）も受け入れる。実在する言葉を弾かないため。アプリの辞書には1文字の言葉を入れない（読み上げが聞き取りにくいため）。
- 1〜4 は何度でも言い直せる。回数は減らさない。
- 回数は「子供が正しく言えた回数」。アプリの言葉は数えない。
- 「きこえた:『○○』」の横に「ちがうよ」を出す。聞き間違いを直す手段。
  - **押せる場面**: 判定の結果が 1〜5 のどれでも押せる。子供が次にマイクボタンを押すまで押せる。
  - **押したとき**: アプリが話している途中なら止める。直前の子供の言葉を無かったことにする。順5 だった場合は、増えた回数を戻し、その言葉とアプリが返した言葉を「出た言葉」から外し、使える最初の文字を1つ前に戻す。そのうえで子供を待つ状態に戻る。
  - 押した回数を、聞き間違いの数として数える（§9）。

### 5.4 文字のつなぎ方（【提案】）
言い終わりの文字から、次に使える最初の文字を決める。迷う場面では**広く受け入れる**。

| 終わり方 | 次に使える最初の文字 | 例 |
|---|---|---|
| ふつうの文字 | その文字 | りん**ご** → ご |
| 長音「ー」 | 伸ばす前の文字、または伸ばした母音 | ぜり**ー** → り / い |
| 小さい文字（ゃゅょ） | 大きくした文字、または拗音ごと | でん**しゃ** → や / しゃ |
| 小さい「っ」 | つ | — |
| ぢ・づ・を | じ・ず・お としても可 | — |

- 濁点・半濁点は区別する（ぶ**た** → た。「だ」は不可）。
- アプリが返す言葉は、表の左側の候補（長音なら伸ばす前の文字、拗音なら大きくした文字）から始める。

### 5.5 聞き取り（【提案】）
- マイクボタンを1回押すと聞き始める。途中結果が1.2秒変わらなければ話し終わりとみなす。最長6秒。
- この検知が子供に合わなければ、「もう一度押して止める」方式に変える。M1 の実機確認で決める（§8）。数値の調整は実装者に任せる。
- 認識エンジンには、次に使える文字で始まる辞書の言葉をヒントとして渡す（最大100語）。
- 認識結果の候補が複数あるときは、最初の文字が合う候補を優先して採用する。
- 聞き取りを始められないとき（通話中、マイク入力が無いなど）は、「いまは きけないみたい。もういちど おしてね」と言って子供の番に戻る。「聞こえなかった」とは別に数える。
- 「おしまい」「ちがうよ」などで流れを打ち切ったら、聞き取りもその場で止めてマイクを離す。
- マイク・音声認識の許可が無いときは、あそぶ画面の代わりに「せっていで ゆるしてね」と設定アプリへのボタンを出す。文字入力の代替手段は v1 では作らない。

### 5.6 アプリの言葉選び（【提案】）
- アプリ内の辞書から、使える最初の文字で始まり、まだ出ていない言葉を無作為に選ぶ。
- 「ん」で終わる言葉は辞書に入れない。
- 終わりの文字から続く言葉が辞書に5語未満しかない言葉（例: 「る」で終わる）は、ほかに候補があれば選ばない。子供を詰まらせないため。
- 候補が無いときは「まいった！」と言い、別の文字で始まる言葉から再開する。回数は続く。

### 5.7 音と声（【提案】）
- アプリの声は OS の読み上げ（`AVSpeechSynthesizer`、日本語、少しゆっくり）。
- 効果音は正解・言い直し・記録更新の3種。音源の用意方法は実装者に任せる。
- 消音スイッチが入っていても、アプリの声は出す（声が出ないと遊べないため）。

## 6. 構成

Swift パッケージ `ShiritoriCore`（`app/` 直下）を、機能ごとのフォルダに分ける。アプリ本体（`app/ShiritoriApp/`）は起動と画面の組み立てだけを持つ。

| 部品 | 役割 | 依存 |
|---|---|---|
| `Rules` | 読みの正規化、つなぎ方（§5.4）、判定（§5.3）。値型と純粋関数だけ | なし |
| `WordBank` | 辞書の読み込みと、アプリの言葉選び（§5.6）。乱数は外から渡す | `Rules` |
| `Session` | 1回のあそびの状態（使える文字、出た言葉、回数）と、その遷移 | `Rules`, `WordBank` |
| `Speech` | 聞く・話すのプロトコルと、OS を使った実装。漢字 → 読みの変換もここ | なし |
| `Play` | `@Observable` な ViewModel と SwiftUI の画面 | 上のすべて |
| `Records` | 最高記録の保存 | なし |

- **状態は1か所**。あそぶ画面の状態は `Play` の ViewModel が持つ1つの列挙型（待機 / アプリが話している / 子供を待っている / 聞いている / 判定結果を見せている / おわり）で表す。旧版のように複数の管理クラスに状態を分けない。
- **時間に依存する処理をテストから切り離す**。聞く・話す・待つはプロトコル越しに呼び、テストでは即座に返る偽物を使う。`DispatchQueue.asyncAfter` と `Timer` は ViewModel で使わない。
- **Swift 6 言語モード**でビルドする。ViewModel と画面は `@MainActor`。
- 【提案】最高記録は整数1つなので `UserDefaults`（保存先は外から渡す）。SwiftData は v1 では使わない。履歴を持つ v1.1 以降で入れる。
- 【提案】ログは `os.Logger` の薄い包み。状態遷移・判定の各段階・聞き取りの開始と結果・エラーを記録する。リポの `CLAUDE.md` §4 が求める「全タップ・全アニメーション・レイアウト再計算」までは記録しない。この差は `CLAUDE.md` を直して合わせる（M0）。
- 依存パッケージは追加しない。`ViewInspector` と `swift-testing` パッケージは外す（Swift Testing はツールチェーン同梱のものを使う）。

### 移植するもの
旧コードから、考え方とテストケースを持ってくる。コードはそのまま写さず、新しい構成に合わせて書き直す。

- `ShiritoriWordNormalizer` の長音・小さい文字の扱い → `Rules`
- `ShiritoriRuleEngine` のつながり判定 → `Rules`
- `WordDictionaryService` の語彙 → `WordBank` の辞書の種（「ん」で終わる語と子供向けでない語は除く）
- 試作の `SpikeKana.reading`（漢字 → 読み）と `SpeechEngines.swift` の認識呼び出し → `Speech`

`HiraganaConverter`（734行）は移植しない。試作の約20行で足りた。足りない例が見つかったら、その例をテストに足して直す。

## 7. 辞書

- 形式: アプリに同梱する JSON。1語につき読み（ひらがな）と、任意で絵文字。
- 規模: 【提案】800語以上。濁音・半濁音を含む各文字に、日本語として無理のない範囲で5語以上。
- 中身: 4〜8歳が知っている名詞。「ん」で終わる語、酒・暴力など子供向けでない語は入れない（旧辞書には「びーる」がある）。
- 作り方: Claude が案を作り、**オーナーが目を通して承認する**（§8 の M2）。
- テストで守ること: 「ん」で終わる語が無い、重複が無い、読みがひらがなだけ、各文字の語数が下限以上。

## 9. 物差し

M1 と M2 の TestFlight 確認で、オーナーが記録する。

| 物差し | 目標 | 取り方 |
|---|---|---|
| 親の手助けなしで続いた回数 | 10回 | あそぶ画面の回数表示 |
| 「ちがうよ」を押した回数（聞き間違い） | 10回のうち2回以下 | おわりの表示に、その回の数を小さく出す |
| 「もういちど いってね」が出た回数（聞き取れず） | 10回のうち2回以下 | 同上 |
| 聞き取りを始められなかった回数 | 目標は置かない。0 でなければ原因を調べる | 同上 |
| 言い直しになった回数（判定の順2〜4 の合計） | 目標は置かない。聞き間違いが言い直しに化けていないかを見る | 同上 |

この小さな数字の表示は M1 と M2 の TestFlight ビルドに入れ、M3 で公開前に外す。
